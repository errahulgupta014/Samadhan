# Admin portal v2 — contract (2026-10-06)

Product request: (1) an **admin login page** (username + password; initial Super Admin `Admin` / `Admin` for now), (2) the Super Admin can **create more portal users with different permissions**, (3) admins can manage **all app content dynamically** from the portal. Three agents work in parallel against this contract: **A1 auth + users**, **A2 content + config (backend and portal UI)**, **A3 mobile**. Shared types are already in `shared/domain.ts` (`AppConfig`, `defaultAppConfig`, `resolveAppConfig`, `Announcement` with Hindi/expiry/status, `settings.appConfig`, `settings.teams`, `BrandingBanner.captionHi`), `shared/community.ts` (`advertiserHi`, `addressHi`, `hoursHi`, `districtHi`, `stateHi`) and `shared/access.ts` (permission `appconfig.manage`, new action names). They are copied to `mobile/shared/`. If a type must change, edit `shared/`, copy the changed files to `mobile/shared/` and tell the others.

## A1 — Admin authentication and users

- New tables (db/schema.ts + drizzle migration, applied once to the local dev DB the way `docs/MOBILE_DEVELOPMENT.md` and the 0003 migration did): `admin_users` (id, owner, username unique case-insensitive, name, email nullable, role, permissions JSON, active, password_hash, salt, iterations, must_change_password, is_default_password, created_at, updated_at, last_login_at) and `admin_sessions` (token hash, owner, user_id, expires, created_at, ip hash/UA optional). Passwords: PBKDF2-SHA256 (WebCrypto, >= 150k iterations, per-user random salt), constant-time compare, never logged or returned.
- `POST /api/admin-auth` (JSON). Cookie `samadhan_admin` (httpOnly, SameSite=Lax, Path=/, Secure on https, 12 h, sliding). `assertOrigin` on every POST.
  - `{action:'login', username, password}` → `{ok:true, user}` + cookie. Generic error "Incorrect username or password." Lockout: 5 failures per username (and per IP bucket) in 15 min → 429 with `retryAfter`.
  - `{action:'me'}` → `{user: AdminUserView|null, defaultPassword:boolean}`; `{action:'logout'}`; `{action:'change-password', currentPassword, newPassword}` (new >= 8 chars, not equal to username, not equal to current; revokes the user's other sessions; clears `is_default_password`).
  - `AdminUserView = {id, username, name, email, role, permissions, active, isDefaultPassword, createdAt, lastLoginAt}` (never a hash).
  - User management, permission `admins.manage`, Super Admin only to grant (reuse `validateAdminGrant` rules in lib/access-policy.ts: `admins.manage` Super-Admin-only; `complaints.manage` needs `complaints.read`; role presets from shared/access.ts; `Custom` = explicit permission list): `{action:'list-users'}`, `{action:'create-user', username, name, email?, password, role, permissions}`, `{action:'update-user', id, name, email, role, permissions, active}`, `{action:'reset-password', id, newPassword}`, `{action:'delete-user', id}`. Rules: usernames 3–32 chars `[A-Za-z0-9._-]`; password policy as above (the bootstrap password is the only exemption); cannot delete/disable/downgrade yourself; the last active Super Admin can never be deleted/disabled/downgraded; disabling, deleting, resetting a password or changing the role/permissions revokes that user's sessions immediately. A newly created user created by a Super Admin may be flagged `mustChangePassword` (default true) so they choose their own password at first login.
- **Bootstrap:** if `admin_users` has no active user, create Super Admin username `Admin` with password from env `ADMIN_BOOTSTRAP_PASSWORD`, default `Admin` (test mode), `is_default_password=true`. While the default password is in use the portal shows a prominent warning banner and a "Change password" call-to-action; the API reports `defaultPassword:true`. Document in the handoff that production must set `ADMIN_BOOTSTRAP_PASSWORD` (or change the password immediately) — never remove the warning.
- **identity() (lib/server.ts):** resolution order = resident bearer token (unchanged) → admin session cookie (new; Principal role `'admin'`, `viewer = {role, permissions, email: username}`) → platform (ChatGPT) identity as before **only when env `ADMIN_PLATFORM_IDENTITY` is not `'off'`** (default on so the existing API tests and dev tooling keep working; document that production should set it to `off`). `userId`/`residentId` for admin principals must not collide with residents. The portal UI must use the admin session only (never the platform identity), so the login page is real in the UI even while the fallback exists.
- **Audit:** extend `admin_access_events` usage (or a new table) to record login success/failure/lockout, logout, user create/update/disable/delete, password reset/change, with actor username, subject, and a HUMAN-READABLE detail (the Audit log currently renders raw JSON; fix that rendering for these rows). Never store passwords.
- **Portal UI:** `app/admin-login.tsx` (new): `/admin` shows the login page when there is no session: logo, "Administrator sign-in", Username, Password (show/hide), error and lockout messages, loading state, keyboard Enter submits, no autofill leakage. After login the portal loads as before. Add to the portal top bar: user name + role, **Change password**, **Sign out** (calls logout then returns to the login page). Add a **Users** page (replace/augment the old "Admin access" page; keep legacy email grants visible as "Platform identity grants (legacy)" read-only if present): table of users (name, username, role, status, last login), create-user form (username, name, email optional, initial password with generator/show toggle, role preset, per-permission checkboxes grouped and labelled in plain English, must-change-password), edit permissions, enable/disable, reset password, delete with confirmation, plain error messages. The Super Admin's own row cannot be edited destructively. Keep the page gated by `admins.manage`.
- Tests: unit tests for password hashing/verify, policy rules (last super admin, self-modification, privilege escalation by a non-Super Admin, username/password validation), lockout, session expiry/revocation; API smoke `tests/admin-auth-api.mjs` (login with Admin/Admin on the dev server, wrong password, lockout then clean-up, create-user with limited permission, that user cannot call `admins.manage` actions and cannot see pages/actions they lack, change-password, logout invalidates the cookie, delete user). Clean up what the test creates (it must not leave the lockout state on `Admin`: use a separate throwaway username for the lockout test).

## A2 — Content and configuration (backend actions + portal UI)

All of these are admin actions on `POST /api/workspace` gated by `actionPermissions` (already declared in shared/access.ts):
- **Announcements (Ward updates)**: `save-announcement {announcement:{id?,title,titleHi,body,bodyHi,priority:'Service notice'|'Important'|'Event'|'Emergency',endsAt?,status:'published'|'archived'}}` (create or edit; keep the old `announcement` action working), `delete-announcement {id}`. Residents see announcements that are published and not past `endsAt`, newest first, with Hindi fields; admin sees all with edit/archive/delete in the portal (page "Announcements", replace the create-only form).
- **Hard delete + safer edits**: `delete-classified {id}`, `delete-activity {id}`, `delete-place {id}` (confirmation in the UI, audit lines, remove their notifications, media stays but becomes unreferenced). **Editing a published ad or activity must keep it published** (today every save forces draft): new items start as drafts; edits preserve the existing status; an explicit unpublish/archive is still available.
- **App config**: `save-app-config {appConfig: AppConfig}` (validate: https-only URLs, phone <= 30 chars, email format, messages <= 300 chars, `minAppVersion` empty or `x.y.z`, booleans) stored in `state.settings.appConfig` and exposed to residents in `data.settings.appConfig` (via `resolveAppConfig`) and publicly (no auth, short cache) at `GET /api/app-config` → `{appConfig, ward, city, contact}` (so maintenance / minimum version / terms links work before login). Portal page **App settings**: org label EN/HI, support phone/email/hours EN/HI, terms and privacy URLs, which tabs (Ads, Activities, City) and Home tiles (Ads, Activities, City, Ward updates) are shown, maintenance mode + messages EN/HI, minimum app version, and the ward/city display labels (`settings.ward`, `settings.city`; extend the existing `settings` action; keep slaHours).
- **Teams**: `save-teams {teams:string[]}` (1–12 names, 2–60 chars, unique) stored in `settings.teams`; the complaint assignee dropdown and Teams page use it (default list from shared/domain.ts); renaming does not rewrite history. Portal UI for it.
- **Hindi fields in the portal forms**: banner `captionHi`, classified `advertiserHi`, place `addressHi`/`hoursHi`, municipality `districtHi`/`stateHi`, activity/ads/places already have most; show a gentle "Hindi missing — the app will show English" hint where Hindi is optional.
- **Dashboard**: the Overview category donut/chart must use the live category list (no hard-coded group list; admin-created categories must not fall into "Other").
- Complaint id prefix must stop hard-coding `W12` if a ward id is available (use the ward number of the resident's ward; keep format `WC-W<ward>-<year>-<id>`), with a unit test; do not break existing ids.
- Keep security invariants (media visibility, assertOrigin, permission gates, resident isolation). Update existing tests; add tests for each new action (validation, permissions for residents and for admins lacking the permission, deletion effects, edit keeps published, announcement expiry/visibility, app-config validation and public endpoint shape, teams, id prefix).

## A3 — Mobile (consumes A2's output)

Read `data.settings.appConfig` (`resolveAppConfig`) and, before login, `GET /api/app-config` (never block startup on it; cache the last good copy in storage; defaults if unreachable):
- **Tabs and Home tiles**: hide Ads / Activities / City tabs and the matching Home tiles per `appConfig.tabs` / `tiles` (Home, Complaints, Profile always visible; the tab bar must keep fitting 375 px; a hidden tab's deep links/notification taps fall back to Home or the inbox).
- **Org label**: replace the hard-coded "Panchayat Samiti / Nagar Parishad" wording (Activities captions, empty states, profile switch copy) with `appConfig.orgLabel` (EN/HI).
- **Ward updates (notices)**: show Hindi (`titleHi`, `bodyHi`), the priority as a coloured chip (Emergency/Important distinct), hide expired, newest first, empty state.
- **Support**: a "Need help?" card on Home (phone tap-to-call, email, hours EN/HI) when any support field is set, and the same on Profile; Profile footer links "Terms of use" / "Privacy policy" (https, `Linking.openURL`) when set. Also use `settings.ward`/`settings.city` labels where the app shows them.
- **Maintenance / minimum version**: if `maintenance.enabled`, show a dismissible-less banner at the top of the app (non-blocking) with the localized message; if the installed app version (`expo-constants` `expoConfig.version`) is lower than `minAppVersion`, show a full-screen "Please update the app" screen (EN/HI) that blocks the app (links nothing; no store URL exists yet). Compare as semver numbers.
- **Hindi**: use `captionHi` for banner captions, `advertiserHi`, `addressHi`, `hoursHi`, `districtHi`, `stateHi` with English fallback.
- The mobile agent must not wait for the backend to finish: code against the contract with typed defaults, verify against the real API once `GET /api/app-config` responds on http://localhost:5173.

## Addendum 2026-10-06 — admin profile photo, App users, Departments, dashboard range
- **Admin profile photo** (`POST /api/admin-auth`): `{action:'set-avatar', mediaId: string|null}` for the signed-in admin; the media must have been uploaded by that admin (`uploader = admin:<id>`); `AdminUserView.avatarMediaId`; column `admin_users.avatar_media_id` (migration `0005_admin_avatar.sql`). The photo is served by `/api/media?id=` with the admin cookie.
- **App users** (permission `residents.manage`; Super Admin and Ward Admin presets): `data.residents: AdminResident[]` (admins with the permission only, real mobile numbers); actions `save-resident {id,name,email,address,wardId,language?,classifiedNotifications?,activityNotifications?}` (mobile read-only) and `block-resident {id,blocked,reason?}` (reason required when blocking, 1–200 chars). A blocked resident gets HTTP 403 `{"error":"Your account has been blocked. Please contact the ward office.","code":"account_blocked"}` on every resident API path and from `verify-otp`/`register`; `send-otp` stays generic; push tokens are deleted on block; the old session token keeps answering the 403 until unblock (unblock deletes sessions, so the old token then gets 401 and the resident signs in again). Blocked residents get no notifications/pushes/message-log entries; their complaints stay visible to admins. `canReadMedia` has a fifth parameter `purpose` ('read'|'attach'): admins with `residents.manage` may READ resident photos but not attach them to content.
- **Departments** (`settings.manage`): `save-departments {departments:[{id?,name,nameHi?,contactName,contactPhone,contactEmail?,active}]}`; stored in `settings.departments` with `settings.teams` kept equal to the active names; visible only to admins with `complaints.read` or `settings.manage`. Phones normalise to 10-digit mobiles (or a 0-prefixed STD landline). Assignment stores `assignee` (name) and `assigneeId`; assignments and every status transition of a department-assigned complaint record a `Department update` communication to the department's phone with status `Not sent · WhatsApp setup pending` (no provider is connected; nothing is delivered). Legacy `save-teams` delegates to the same store.
- **Dashboard range:** Overview defaults to the current month; presets Today / Last 7 days / Last 30 days / Last month / This year / Custom (From–To, max 366 days); counts by `createdAt`; helpers in `lib/date-range.ts`; range kept in sessionStorage.

## Addendum 2026-10-07 — closure code, complaint numbers, multi-ward, delete-resident, tables/filters
- **Closure code:** `settings.closureOtp` (admins with `settings.manage` only; residents never receive it). Undefined = default `123456`; `''` disables the universal code (a random code per complaint is issued). Set through the existing `settings` action (`closureOtp` 4–8 digits or empty). While a universal code is configured, `verify-closure` accepts it for any complaint in Resolution Proposed (no expiry/lock). Admin button text is 'Request closure'.
- **Resolution target:** still `settings.slaHours` (stored as hours); the portal edits it as DAYS (default 2 = 48 h). The target date of a complaint is `createdAt + slaHours`; changes apply to complaints submitted afterwards.
- **Complaint numbers:** new ids are `JSS/<yy>/W<ward>/<n>` (yy = India-time year, W + sanitised ward number, `W0` if unknown; n counts per ward per year starting at 1). Legacy `WC-W…` ids are untouched. `Complaint.wardId` is stored from the resident profile; `wardLabel` is computed at read time.
- **No default ward:** `seedWorkspace()` has no wards and blank `settings.ward/city/contact`; `LIVE_CONTENT_VERSION = 2` blanks old seeded 'Ward 12' / 'Jaipur' / contact text once. Admins with `complaints.read` receive the ward list (no member photo ids) for the ward filter. `GET /api/app-config` ward/city/contact are legacy and empty.
- **delete-resident** `{id}` (permission `residents.manage`): removes the profile (incl. blocked flag), notifications, sessions, push tokens and pending OTP; complaints stay anonymised ('Former resident', mobile masked to the last 4 digits, `residentId` kept); communication entries for that number are masked; uploads re-assigned to `deleted:<id>`; returns `{id, deleted:true}`; old tokens answer 401; the number can register again as a new profile (old complaints reappear).
- **Admin tables:** every record table has View / Edit / Active-Inactive / Delete (where the backend supports it: categories cannot be deleted; the city profile has no delete) with add/edit in popups, and the shared `FilterToolbar` (`app/form-bits.tsx`, helpers in `app/table-filters.ts`): search + select filters + date ranges + Clear filters + result count; the Complaints page uses it with filters from `lib/complaint-filters.ts`. Page 'Users' is now 'Admin Users'; the Add admin user popup pre-selects `DEFAULT_NEW_ADMIN_PERMISSIONS` (complaints.read, complaints.manage, announcements.manage) and any change switches the role to Custom (`lib/admin-permission-form.ts`).

## Addendum 2026-10-07 (later) — admin closes with the OTP; Super Admin deletes; Departments in Administration
- **Closure by the administrator:** after 'Request closure' (status Resolution Proposed) a closure OTP is issued for the resident's WhatsApp number (communication entry 'Closure OTP', the code itself is never written to the log). The resident gives the code to the officer, who enters it in the portal: `admin-verify-closure {id, code}` (permission `complaints.manage`, admin role only) closes the complaint (history note 'Resolution confirmed: the resident's closure OTP was verified by the administrator.'); `admin-issue-closure-code {id}` resends (60 s cooldown). The configured universal code (`settings.closureOtp`, default 123456) always works; otherwise the per-complaint code (5 minutes, 5 tries). `validateTransition` now requires only a verified OTP for 'Closed' (a direct close without OTP is refused). The resident app no longer asks for the code; it explains that the closure OTP was sent to WhatsApp and should be shared with the officer only if the problem is fixed ('Not resolved' still reopens). The old resident actions `issue-closure-code` / `verify-closure` remain in the API.
- **Delete is Super Admin only:** `lib/workspace-api.ts` refuses `delete-announcement`, `delete-classified`, `delete-activity`, `delete-place`, `delete-ward`, `delete-resident`, and list saves that remove a banner (`save-banners`, `restoreDefault` with custom banners) or a department (`save-departments` missing existing ids) with 403 'Only a Super Admin can delete records.' unless `viewer.role === 'Super Admin'`; deleting admin users already needs a Super Admin. Portal tables show Delete only to Super Admins, always behind a confirmation dialog.
- **Navigation:** WORKSPACE = Overview, Complaints, Reports; ADMINISTRATION = Departments, Announcements, Categories, Classifieds, Activities, City & places, App users, Admin Users, App settings, Settings (the group heading is placed by group, not by position).
